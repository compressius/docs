# Security and data handling

CMX is a local gateway, but a model request still travels to the model provider you selected. The data path is:

```text
Coding client → CMX on loopback → selected model provider
```

CMX Cloud is not in that request path. It receives aggregate usage metrics, not prompts, responses, source code, session data, or provider API keys.

## Gateway access

The gateway binds to `127.0.0.1` by default and rejects non-loopback listen addresses. Local management routes also require an owner token and validate Host and Origin. Binding to loopback does not turn a provider API into a public endpoint.

## Credentials

Your coding client owns provider sign-in. CMX forwards provider credentials in memory for requests and does not persist or log provider API keys. The native client may store its own authentication files according to that client's design; CMX does not delete them on logout or uninstall. `cmx login` is a separate, optional CMX account sign-in for the dashboard.

Do not place provider API keys in `config.json`, terminal screenshots, issue reports, or support emails.

## What is stored locally

CMX keeps local configuration, usage and session records, compression metadata, and cached summaries in its user data directory. It does not offer raw request logging; `cmx logs` describes the available diagnostics. The **lossless content vault** is disabled by default. If you enable it, selected original tool content removed by local optimization is stored in the local SQLite database. `cmx vault list` and `cmx vault show <id>` can inspect that content; `cmx vault prune` enforces its retention count. Treat the data directory as sensitive and use owner-only filesystem permissions.

`cmx uninstall` removes CMX's local data by default. `--keep-data` retains it. See [Undo and uninstall](/uninstall).

## Cloud and updates

Local proxy use does not require a CMX account. An account is needed for account-linked dashboard statistics. Cloud synchronization uses aggregate counters only. Update checks do not install a new binary automatically; `cmx upgrade --install` is an explicit action. Published binary downloads include SHA-256 checksums. A checksum verifies a file against the published checksum manifest; it is not a code-signing claim.
